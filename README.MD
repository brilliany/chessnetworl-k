# Scalability Transition Plan for `chessnetworl-k`

## Current Architecture Summary

After reviewing your codebase, here's what exists today:

| Layer | Current Technology | Notes |
|---|---|---|
| **Backend / Server** | Rust + **Actix-Web** | Serves HTML/CSS/JS as static files, handles REST API, manages sessions with `unsafe` global mutable state |
| **Frontend** | Pure **JavaScript** + hand-written **HTML/CSS** | DOM manipulation, `fetch` calls, no framework or bundler |
| **Game Logic** | Rust (`chessboard.rs`, `movegenerator.rs`, `move.rs`) | Bitboard representation, move generation, board state |
| **Engine** | Rust (`engine.rs`, `heuristics.rs`) | Alpha-beta with iterative deepening, transposition tables, killer moves |
| **Config** | `config.yml` (via `config` crate) | Server address/port, mode selection |

Key scalability concerns in the current codebase:
- The Actix server manually serves every static file via dedicated route handlers (one per image, CSS file, JS file)
- Session management uses `static mut GLOBAL_SESSIONS` with `unsafe` blocks — not thread-safe
- JSON is built by hand with string concatenation instead of serialization
- Frontend and backend are tightly coupled in a single monolith

## Transition Plan

### Phase 1 — Separate the Rust Codebase into Library vs. Server

**Goal:** Decouple the performance-critical game/engine logic from the server layer so it can be consumed by any backend.

**What to do:**
- Extract `chessboard`, `movegenerator`, `move`, `engine`, `heuristics`, and `constants` into a standalone Rust **library crate** (e.g., `chessnetwork-core`).
- This crate exposes a clean public API: `new_game()`, `make_move()`, `get_legal_moves()`, `get_engine_move()`, `get_board_state()`, etc.
- The library can then be consumed either as a native dependency or compiled to **WebAssembly**.

**Tools:**

| Tool | Purpose | Why it fits |
|---|---|---|
| **Cargo workspaces** | Organize `chessnetwork-core` (lib) and the backend as sibling crates | Built-in Rust feature, zero overhead |
| **wasm-pack** | Compile the core library to WebAssembly for browser use | Lets the engine run client-side if desired, keeping the Rust performance |
| **wasm-bindgen** | Generate JS bindings for the WASM module | The standard for Rust↔JS FFI in WASM |

**Alternative:** If WASM client-side execution isn't needed immediately, skip `wasm-pack` and only expose the library as a Rust crate consumed server-side. WASM can be added later without restructuring.

---

### Phase 2 — Replace the Backend

**Goal:** Move from Actix-Web (which is currently doing double duty as static file server + API + session manager) to a more established backend system that handles routing, middleware, session management, and static serving properly.

#### Recommended: **Axum** (Rust)

Since the game logic is in Rust, staying in the Rust ecosystem avoids FFI overhead and keeps a single language on the backend. Axum is the natural successor choice:

| Tool | Purpose | Why it fits |
|---|---|---|
| **Axum** | HTTP framework | Built on `tokio` and `tower`, production-grade, excellent middleware ecosystem, strong typing. More modular than Actix-Web. |
| **tower-sessions** or **axum-extra** | Session management | Replaces the `unsafe` global `HashMap` with proper session middleware backed by cookies + a store |
| **tower-http** | Static file serving, CORS, compression | `ServeDir` eliminates the need for one handler per static file |
| **serde / serde_json** | Proper JSON serialization | You already have `serde` in `Cargo.toml` — use `#[derive(Serialize)]` instead of hand-building JSON strings |

**Alternatives:**

| Alternative | Trade-off |
|---|---|
| **Actix-Web (refactored)** | You already use it; a deep refactor (proper state via `web::Data<Arc<Mutex<...>>>`, `actix-files` for static serving) could achieve the same result without switching frameworks. Lower migration cost, but Actix's actor model is heavier than needed here. |
| **Go (net/http + chi/gorilla)** | Very good for HTTP APIs, but introduces a language boundary with the Rust engine (FFI via CGO or a sidecar process). Adds complexity for a solo project. |
| **Node.js (Fastify/Express)** | Would pair naturally with a JS/TS frontend monorepo, but the Rust engine would need to be called via WASM or a subprocess. Adds a serialization layer. |
| **Python (FastAPI)** | Excellent DX, but same FFI concern. Would only make sense if you wanted rapid API prototyping and were willing to call the Rust engine via PyO3. |

**Verdict:** **Axum** fits best because it keeps the backend in Rust (zero-cost integration with `chessnetwork-core`), has a cleaner API than Actix for this use case, and its middleware system (`tower`) is the de facto standard in the Rust async ecosystem.

### Phase 3 — Revamp the Frontend

**Goal:** Replace the hand-written JavaScript + HTML with a modern framework that provides component architecture, reactive state, and a proper build pipeline.

#### Recommended: **SolidJS** + **TypeScript**

| Tool | Purpose | Why it fits |
|---|---|---|
| **SolidJS** | UI framework | Fine-grained reactivity with no virtual DOM — extremely fast, small bundle (~7KB), close-to-the-metal feel that matches the project's performance-oriented spirit. Simpler mental model than React for a solo dev. |
| **TypeScript** | Type safety | Catches bugs at compile time; chess state types map cleanly to interfaces |
| **Vite** | Build tool / dev server | Instant HMR, out-of-the-box TS + SolidJS support, fast production builds |
| **solid-styled-components** or **vanilla CSS modules** | Styling | Keeps styles scoped per component; CSS modules have zero runtime cost |

**Alternatives:**

| Alternative | Trade-off |
|---|---|
| **Svelte** | Also compiles away the framework, very small output. Excellent DX, slightly more "magic" (compiler-driven reactivity). A strong contender — similar performance profile to Solid, and the single-file component format is very ergonomic for a solo project. |
| **React** | Massive ecosystem, but heavier (virtual DOM), more boilerplate. Overkill for a chess UI that doesn't need complex state trees. |
| **Vue 3** | Good middle ground, but the Composition API is still heavier at runtime than Solid/Svelte. |
| **Leptos** (Rust → WASM full-stack) | Write the frontend *in Rust* too. Compelling for this project since you already know Rust, but the WASM DX for UI is still less mature than JS frameworks. Worth watching. |

**Verdict:** **SolidJS** or **Svelte** — either is an excellent fit. SolidJS edges ahead on raw performance and predictability (no compiler magic), Svelte edges ahead on ergonomics and DX. Both produce tiny bundles, both have Vite integration. Pick based on personal preference.

### Phase 4 — Repository Separation

**Goal:** Split into two (or three) repositories to maintain separation of concerns.

#### Recommended Structure:

```
brilliany/chessnetwork-core     # Rust library crate (game logic + engine)
brilliany/chessnetwork-api      # Rust backend (Axum) — depends on chessnetwork-core
brilliany/chessnetwork-web      # Frontend (SolidJS/Svelte + TypeScript)
```

| Tool | Purpose | Why it fits |
|---|---|---|
| **Git submodules** or **Cargo git dependencies** | Let the API repo depend on `chessnetwork-core` without publishing to crates.io | Simple, no registry needed for a solo project |
| **GitHub Actions** | CI/CD for each repo independently | Free for public repos, per-repo workflows keep builds fast |
| **Docker / docker-compose** | Local development of all three together | One `docker-compose up` starts the backend + frontend dev server |
| **OpenAPI / JSON Schema** | Define the API contract between frontend and backend | Generates TypeScript types from the API spec, preventing contract drift |

**Alternative: Monorepo with workspaces**

If three repos feels like too much overhead for a solo project:

| Tool | Purpose |
|---|---|
| **Cargo workspace** (root) | Houses `core` and `api` as workspace members |
| **npm/pnpm workspace** | Houses the frontend alongside the Rust workspace |
| **Turborepo** or **Nx** | Orchestrates builds across the JS + Rust boundary in a single monorepo |

This keeps everything in one repo while still maintaining logical separation. You lose independent versioning but gain simpler cross-project changes.

### Phase 5 — API Design & Communication

**Goal:** Define a clean, stable REST (or WebSocket) API between frontend and backend.

Currently, the API surface is:

| Endpoint | Method | Purpose |
|---|---|---|
| `/api/populate-board` | GET | Get board state |
| `/api/possible-moves` | GET | Get legal moves for a piece |
| `/move-piece` | POST | Make a player move |
| `/api/make-engine-move` | GET | Trigger engine move |
| `/api/get-session` | GET | Get session info |

**Suggestions:**

| Tool | Purpose | Why it fits |
|---|---|---|
| **RESTful redesign** | Clean up endpoints to follow REST conventions (`GET /api/games/:id`, `POST /api/games/:id/moves`, etc.) | More intuitive, standard |
| **WebSockets** (via `axum`'s built-in support or `tokio-tungstenite`) | Push engine moves to the client instead of polling | The engine search can take time — WS lets you stream progress or push the result |
| **serde + utoipa** | Auto-generate OpenAPI docs from Rust types | Keeps the API contract in sync with the code |

**Alternative:** **tRPC-style** (if using a TypeScript backend) or **gRPC** (if you ever want inter-service communication). Both are heavier than needed right now.

## Migration Order (Suggested)

```
Step 1 ──► Extract chessnetwork-core as a library crate (Cargo workspace)
           No external changes — same behavior, cleaner internal structure.

Step 2 ──► Fix the backend in-place
           • Replace unsafe session management with Arc<Mutex<HashMap>>
           • Use serde for JSON serialization
           • Use actix-files or tower-http for static file serving
           • Add proper error handling

Step 3 ──► Migrate backend from Actix to Axum (optional but recommended)
           Consume chessnetwork-core as a workspace dependency.

Step 4 ──► Build the new frontend
           • Scaffold with Vite + SolidJS/Svelte + TypeScript
           • Reimplement the chessboard UI as components
           • Connect to the (now cleaner) API

Step 5 ──► Separate into repositories (or keep as monorepo with workspaces)
           Add CI/CD per component.

Step 6 ──► Add WebSocket support for engine moves
           Replace the polling GET with a push model.
```

> **Note on being solo:** None of these steps require a team. The migration is designed to be incremental — each step leaves the project in a working state. The heaviest lift is Step 4 (frontend rewrite), but with SolidJS/Svelte + Vite the scaffolding is minimal. Steps 1–2 can be done in a single session and immediately improve code quality.
